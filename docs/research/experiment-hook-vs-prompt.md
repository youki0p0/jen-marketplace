# 検証計画：hook で強制した検証 vs プロンプトでお願いした検証

状態: 未実施。別のチャットで回すための引き継ぎ。
作成: 2026-10-24 ・ 対象: jen-marketplace v4.0.0

## 何が分かっていないのか

`docs/jen-v4-design.md` の第8節に、こう書いてある。

> 「hook で強制した検証」と「プロンプトでお願いした検証」を比べて、完了率がどう違うかを測った研究は、今回の調査では見つからなかった。

つまり v4 の中心にある判断は、裏づけのないまま置かれている。この計画はそれを測る。

比べる相手がはっきりしている点が重要である。Anthropic 自身は、機能リストが書き換えられるのを強い言い回しの指示で守っている（`effective-harnesses-for-long-running-agents`）。v4 は Stop hook で守っている。どちらが効くかを誰も比べていない。

## 素直にやると交絡する

「hook あり」対「hook なし」で比べたくなるが、これでは答えが出ない。hook を入れた側には台帳もあるので、測っているのは「台帳＋hook」対「何もなし」になる。差が出ても、それが強制のせいか、受入条件を項目に割ったせいか、分けられない。

分けるには4つの条件が必要である。

| | 台帳 | ゲート | プロンプト |
|---|---|---|---|
| P | なし | — | 普通に「確認してから完了と言って」 |
| P+ | なし | — | 強い言い回し（Anthropic と同じやり方） |
| L | あり | `"gate": "off"` | 普通 |
| G | あり | 有効 | 普通 |

- **P+ 対 G** — これが本題。強い指示と機械の強制を直接比べる
- L 対 G — 強制だけを切り出す（台帳は両方にある）
- P 対 L — 項目に割ることの効果だけを切り出す
- P 対 P+ — 言い回しを強めることの効果

P+ の文言は Anthropic の実物に寄せる。例:「テストを削除したり編集したりすることは許されない。受入条件のすべてを満たしたことを確認せずに完了と言ってはならない。」

## 測るもの（ここが一番壊れやすい）

**台帳に判定させてはいけない。** ゲートが完了を決めている条件で、完了したかを台帳に聞けば、G が定義上勝つ。循環する。

やり方:

1. 課題ごとに受入判定スクリプトを先に書く（実行して pass / fail が出るもの）
2. エージェントには見せない。作業するリポジトリの中にも置かない（読んで狙い撃ちされる）
3. エージェントが「完了しました」と言った時点のツリーに対して、あとから実行する
4. 結果は pass / fail の2値

この「先に書く」が守られないと、あとから基準が動く。計画のいちばん重要な部分である。

### 一緒に測るもの

Jain の実験で分かっているのは、ハーネスの最大のリスクが余計にかかる費用と時間だということである。ハーネスを付けた側は1回あたり平均で1,707万トークン・19分を余分に使い、付けない側の約16倍になった。

**完了率が上がっても、16倍かかるなら勝ちではない。** だから必ず両方出す。

| 測るもの | 取り方 |
|---|---|
| トークン | Claude Code のセッション情報から |
| 実時間 | 開始と終了の時刻 |
| 委譲回数 | `evidence_ledger.py budget`。ただしプラグインとして入れた状態でないと `post_tool_log.py` が動かず「判定不能」になる |
| 往復回数 | セッションのターン数 |

委譲回数は P / P+ では台帳が無いので取れない。hook のログから直接数える必要がある。

## どのモデルで回すか

sonnet か haiku で回す。

設計書の予想は「安いモデルでは効果が出て、opus では消える」である。opus で回すと両方成功して何も分からない可能性が高く、しかも高い。

余裕があれば opus でも少数回し、効果が消えることを確かめる。消えれば、予想が当たったという別の結果になる。

## 課題の選び方

| 条件 | 理由 |
|---|---|
| 受入条件が3〜5個に割れる | 1個だけ飛ばす、が起きる余地を作る |
| 飛ばしたことがスクリプトで検出できる | 好みの判断が入ると測れない |
| 素の成功率が3〜7割 | 全部成功／全部失敗だと差が見えない |

Jain の結果（低価格モデルで素 3/10 → ハーネス付き 10/10）が、狙う難易度の目安になる。

飛ばされやすい受入条件の例:

- 空入力のときの扱い
- エラー時に 500 ではなく 400 を返す
- 既存のテストを壊していない
- 2回実行しても同じ結果になる

課題は5〜8本。全条件で同じ課題を使う。

## 何回回せば分かるか

2値の結果を比べるので、必要な回数は差の大きさで決まる。

| 見たい差 | 1条件あたりの回数（検出力80%・α=0.05）|
|---|---|
| 50ポイント（30% → 80%）| 約15回 |
| 30ポイント（40% → 70%）| 約42回 |
| 15ポイント | 約170回 |

4条件なので、30ポイントを見たいなら合計170回ほど必要になる。

**5回ずつでは何も分からない。** 回数が足りないときは、始める前に「この回数では○○ポイント以上の差しか見えない」と書いておき、差が出なかったときに「効果がなかった」ではなく「分からなかった」と書く。これを先に決めておかないと、ノイズを結果として読んでしまう。

## 始める前に紙に書くこと

この実験は、**作った本人が測る**。v4 が良く見えてほしいという動機が働く位置にいる。だから手順を先に固定する。

書いておく項目:

- 4条件の内容（プロンプトの文言は一字一句）
- 課題の一覧と、受入判定スクリプト
- 1条件あたりの回数
- 主要な結果は「受入判定スクリプトの pass 率」であること
- 差が出なかったときに何と書くか

そのあと動かす。

## やり方の細かい点

- 1回ごとに新しいセッションで始める（前の回の文脈を持ち込まない）
- 課題の順番は条件ごとにばらす
- 受入判定は全部回し終わってからまとめて実行する。1回ごとに見ると、次の回の扱いが変わる
- エージェントには、仕組みの違い以外のことを伝えない

## 分かっていても直せない限界

先に書いておく。

- 操作するのが1人、コードの種類も1つなので、ほかの環境に当てはまるとは言えない
- Jen に対する結果であって、ハーネス一般の結果ではない
- モデルは更新される。結果に日付を付ける
- P+ の文言は自由に決められる。もっと強い言い回しなら差が消えるかもしれない。「強い指示では足りない」と結論するときは、使った文言をそのまま載せる

## もう一つの経路：文献をもう一度探す

実験の前に、本当に無いのかを確かめ直す価値がある。見つかれば実験そのものが要らなくなる。

探す向きの候補:

- ソフトウェア工学側の用語（`guardrail` `enforcement` `runtime check` `process conformance`）
- エージェント評価側の用語（`stopping criterion` `premature termination` `self-assessment calibration`）
- 人間の研究から（チェックリストの強制 vs 推奨。医療・航空の分野に蓄積がある）
- 「指示に従う度合い」を測った研究（`instruction following` の失敗率。強い言い回しの効果を測っているものがあるか）

4番目が近いかもしれない。プロンプトの強さと従う率の関係を測った研究があれば、P 対 P+ の部分は実験せずに済む。
